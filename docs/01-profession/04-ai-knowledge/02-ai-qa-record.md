# AI 概念问答记录

## Q1: LLM 输出的内容是如何保证逻辑性的

LLM 保证输出逻辑性主要通过以下几个层面的技术机制：

### 训练阶段：从语料中学习逻辑模式

LLM 在海量文本（书籍、论文、代码、百科等）上进行预训练，这些语料本身包含大量逻辑推理结构。模型通过统计学习，掌握了因果、递进、对比、分类等逻辑关系的语言表达模式。**它并非真正"理解"逻辑，而是学会了逻辑的"语言外壳"**。

### 注意力机制：捕捉上下文关联

Transformer 的自注意力机制让模型在生成每个 token 时，能关注到前文所有相关内容，从而保持前后文一致。多头注意力可以同时关注不同维度的语义关系（如指代、因果、转折），这是输出连贯性的技术基础。

### 思维链（Chain of Thought）

这是近年来提升逻辑性的关键突破。模型被引导或训练为"逐步推理"，先输出中间推理步骤，再得出结论。典型代表是 DeepSeek-R1、OpenAI o1 等推理模型。思维链让模型：
- 将复杂问题分解为子步骤
- 中间结果可以被后续步骤引用
- 推理过程可追溯、可验证

### RLHF：人类反馈强化学习

通过人类对模型输出进行排序和反馈，再用强化学习优化模型，使其倾向于产出**逻辑清晰、条理分明**的回答，而非散漫随意的文本。这是 ChatGPT 等模型"对齐"人类表达习惯的核心手段。

### 推理阶段的约束技术

- **上下文窗口管理**：确保相关上下文不被截断
- **解码策略**：如 temperature、top-p 控制随机性，低温度下输出更确定性、更逻辑
- **结构化提示**：通过 system prompt 约束输出格式（如"分点论述""先分析后总结"）
- **工具调用与 RAG**：引入外部知识检索，减少幻觉导致的逻辑断裂

### 仍存在的局限

LLM 的"逻辑"本质是**概率预测**，并非形式化的逻辑推理，因此仍会出现：
- **幻觉**：编造看似合理但实际错误的事实
- **长链条推理失效**：多步推理时错误累积
- **数学/符号推理不稳定**：缺乏真正的符号演算能力

这也是为什么 Claude 4 引入神经符号架构、DeepSeek-R1 强化可验证推理链等方向成为当前研究热点——试图让模型的逻辑从"看起来合理"走向"真正可验证"。

## Q2: Agent 里面调用的 Tool，也是需要依赖三方平台返回结果的吗

是的，**大部分情况下是的**，但具体情况取决于 tool 的类型。

### 需要依赖三方平台返回结果的 Tool

这是最常见的类型，Agent 调用 tool 时本质上是向外部服务发起请求：

| Tool 类型 | 依赖的平台 | 示例 |
|-----------|-----------|------|
| 搜索引擎 | Google、Bing、百度 | 检索实时信息 |
| API 调用 | 企业 API、SaaS 服务 | 查天气、下单、查数据库 |
| 代码执行 | Python 解释器、Docker | 执行计算、运行脚本 |
| 文件操作 | 本地文件系统 | 读写文件 |
| 浏览器自动化 | 网页 DOM | 模拟点击、填表 |
| 知识库检索 | 向量数据库、搜索引擎 | RAG 检索 |

这些 tool 的执行结果**完全依赖外部系统的返回**，Agent 无法控制。如果平台挂了、API 限流了、返回了错误数据，Agent 就得依赖容错机制来处理。

### 不需要依赖三方平台的 Tool

有些 tool 是纯本地的，不依赖外部网络：
- **本地计算**：数学运算、字符串处理、正则匹配
- **本地工具链**：本机 git 操作、本地脚本执行
- **内存/状态管理**：维护对话状态、短期记忆

### 关键点

**Agent 本身是"无状态"的**，它不存储知识，只是编排调用 tool 的逻辑。因此：
1. Tool 的可靠性直接影响 Agent 的输出质量
2. Tool 的延迟影响响应速度
3. Tool 的权限决定 Agent 的能力边界

## Q3: 调用方是 Agent 吗，他需要本地调用，这个能力是 LLM 本身不具备的吧

**完全正确**。调用方是 **Agent 框架/运行时（Runtime）**，不是 LLM。LLM 只负责"决策"，执行能力完全由 Agent Runtime 提供。

### LLM 本质上不具备任何"执行"能力

LLM 只是一个**文本生成器**，它：
- 不能访问网络
- 不能读写文件
- 不能执行代码
- 不能操作浏览器

### Agent Runtime 提供的能力

| 能力 | 谁提供 |
|------|--------|
| 解析 LLM 输出的 tool 调用指令 | Agent Runtime |
| 路由到对应的 tool 实现 | Agent Runtime |
| 执行本地代码/脚本 | Agent Runtime（调用本地 Python/Shell） |
| 发起网络请求到三方 API | Agent Runtime（HTTP 客户端） |
| 管理文件系统操作 | Agent Runtime（OS 系统调用） |
| 浏览器自动化 | Agent Runtime（Playwright/Selenium） |
| 将 tool 结果格式化返回给 LLM | Agent Runtime |

差异不在 LLM，而在 Runtime 给它配置了哪些 tool。

## Q4: LLM 跟 Agent Runtime 是如何交互的

整个流程是一个 **Tool Calling（工具调用）循环**：

1. **用户输入** → Agent Runtime 接收用户请求
2. **Runtime 构造 Prompt** → 在发送给 LLM 的 prompt 中附加所有可用工具的 Schema（工具名称、参数定义、功能描述）
3. **LLM 输出 Tool 调用指令** → LLM 输出结构化文本（通常是 JSON），如 `{"tool": "search_web", "parameters": {"query": "今天天气"}}`，LLM 只负责决策调用什么，不负责执行
4. **Runtime 执行 Tool** → Agent Runtime 解析指令，自己调用对应的 tool（本地代码、网络 API、文件操作等），获取实际结果
5. **结果回传给 LLM** → Runtime 将 tool 执行结果格式化后，再次发送给 LLM
6. **LLM 生成最终回答** → LLM 结合 tool 返回的真实数据，生成完整回答
7. **返回给用户** → Runtime 将最终回答呈现给用户

这个循环可以**迭代多次**（比如先搜索、再计算、再搜索），每一次都是"LLM 决策 → Runtime 执行 → 结果回传"的模式。LLM 始终不直接接触外部世界，所有的"手脚"工作都由 Runtime 完成。

## Q5: MCP 是什么

MCP（Model Context Protocol，模型上下文协议）是由 Anthropic 在 2024 年底提出的一套**开放标准协议**，旨在为 AI 模型与外部数据源、工具之间建立统一、安全的连接机制。到 2026 年已成为 AI 工具集成的事实标准之一。

**一句话理解：MCP 就是 AI 应用的"USB-C 接口"**。

### 解决什么问题

在 MCP 出现之前，AI 应用集成工具是一片混乱：
- OpenAI、Anthropic、Google 各有各的 Function Calling 格式，互不兼容
- 工具是**硬编码**进应用的，换个模型就要重写集成代码
- 每个工具的权限、认证、错误处理各自为政

MCP 把 **M×N 的集成问题降到了 M+N**：工具开发者只需实现一次 MCP Server，就能被所有支持 MCP 的客户端使用。

### 核心架构

| 角色 | 职责 |
|------|------|
| MCP Server | 暴露三类能力：Tools（工具）、Resources（资源）、Prompts（提示词模板）；实现具体逻辑 |
| MCP Client | AI 应用或 IDE（如 Claude Desktop、Cursor、TRAE），发现并调用 Server 提供的工具 |
| 传输层 | stdio（本地进程通信）、HTTP+SSE（远程通信）、WebSocket（双向流式） |

通信协议基于 **JSON-RPC 2.0**。MCP 本质上是 Agent Runtime 调用 Tool 环节的标准化协议。

### 2026 年生态

| 类别 | 代表 MCP Server |
|------|----------------|
| 文件系统 | @mcp/filesystem |
| 版本控制 | @mcp/github、@mcp/gitlab |
| 数据库 | @mcp/postgres、@mcp/sqlite |
| 浏览器 | @mcp/playwright |
| 通信 | @mcp/slack、@mcp/gmail |
| 搜索 | @mcp/brave-search、@mcp/tavily |
| 知识管理 | @mcp/notion、@mcp/obsidian |

## Q6: 创建新 Agent 和使用通用 Agent + Skills 有什么区别

### 创建新 Agent = 定制化方案

从头搭建一个**专用 Agent**，包括：
- 专属的 System Prompt（针对特定任务精心设计）
- 专属的 Tool 集合（只加载需要的工具）
- 定制的工作流（特殊执行逻辑、多步骤编排、状态管理）
- 独立的部署和配置

**优点**：任务适配度极高，适合垂直场景
**缺点**：开发成本高，能力难以跨 Agent 复用

### 通用 Agent + Skills = 插件化方案

有一个**统一的 Agent Runtime**，通过**动态加载不同的 Skill 包**来适应不同任务：
- 通用 System Prompt（基础角色定义）
- 可插拔 Skills（独立能力模块，按需加载）
- 统一的工具调用机制（如 MCP）
- 一套部署，多场景复用

**优点**：开发成本低，新场景只需添加 Skill，Skills 可跨场景复用
**缺点**：灵活性略逊于完全定制

### 对比

| 维度 | 创建新 Agent | 通用 Agent + Skills |
|------|-------------|-------------------|
| 开发成本 | 高 | 低 |
| 灵活性 | 高 | 中 |
| 任务适配度 | 高 | 中高 |
| 复用性 | 低 | 高 |
| 维护成本 | 高 | 低 |
| 类比 | 专门建一座工厂 | 通用 3D 打印机 + 换耗材 |

### 选型建议

- **选创建新 Agent**：高度专业化的长期任务，需要深度定制工作流（如企业级自动化流水线）
- **选通用 Agent + Skills**：需要快速覆盖多种任务场景，能力灵活组合和复用（如 TRAE 的架构）
- **两者不是互斥的**：很多平台先从通用 Agent + Skills 起步，再将高频场景沉淀为专门的定制 Agent
